# План переноса контроллера ворот на ESP32-S3 N16R8

> Замена STM32F103 (HAL/CubeMX). Платформа: **ESP-IDF v5.x** (FreeRTOS), язык — C (с возможностью
>компонента на C++ для Wi-Fi/Bluetooth стека). Makefile отложен — используется `idf.py` + CMakeLists.txt.

---

## 1. Почему выбор оправдан: ресурсы ESP32-S3 N16R8 vs текущие нужды проекта

| Ресурс | STM32F103 (текущий) | ESP32-S3 N16R8 (целевой) |
|---|---|---|
| Ядро | 1× Cortex-M3, 72 МГц | 2× Xtensa LX7, до 240 МГц |
| Flash | ~64–256 КБ | **16 МБ** (QIO) |
| RAM | 20–64 КБ | 512 КБ SRAM + 8 КБ eFuse/RTC + **PSRAM 8 МБ (Octal)** |
| Wi-Fi / BT | нет | 802.11 b/g/n + BLE 5 (Long Range) |
| Шифрование | нет | HW AES/SHA/RSA, Secure Boot v2, Flash Encryption |
| Периферика | TIM1-4, ADC1, SPI1, USART | 4× SPI, 2× I2C, 2× UART, 2× ADC (12 бит, аппаратный фильтр), PWM LED (8 каналов ×16 бит), MCPWM (моторы!), RMT (IR/OneWire), PCNT (энкодеры!), USB-OTG/Serial-JTAG, TWAI (CAN), I2S, RTC, WDT ×2, ULP |
| Энергосбережение | LPM вручную | Deep-sleep ~10–20 мкА, light-sleep, modem-sleep |

Ключевые «родные» блоки ESP32-S3 идеально ложатся на задачи проекта:

- **PCNT** (Pulse Counter unit, 8 шт.) — аппаратный quadrature-декодер энкодера вместо
  программного TIM3->CNT из `init.c` (там же были баги с переполнением).
- **MCPWM** — генерация комплементарных сигналов с dead-time и автозащитой для H-моста
  вместо грубого включения реле MOTOR_OPEN/MOTOR_CLOSE.
- **LEDC PWM** — диммирование освещения, мягкий разгон мотора (если драйвер ШИМ).
- **ADC + аппаратный фильтр** — измерение тока трансформатором (аналог `adc.c`) без софтверного RMS по таймеру.
- **Регистры RTC + EXT0/EXT1 wakeup** — реакция на концевики/кнопки в deep-sleep.
- **TWAI** — шина CAN для выносных кнопок/датчиков (альтернатива RS-485).

## 3. Максимально возможный набор функций (супер-set для ESP32-S3 N16R8)

### 3.1 Базовое управление воротами (перенос текущего функционала)
1. Открыть / Закрыть / Стоп (кнопки, удалённо, по расписанию).
2. Определение позиции по энкодеру (**PCNT**, 32-битный счёт, без переполнения из `init.c`).
3. Концевые выключатели OPEN/CLOSE + барьерный луч как аппаратное ограничение.
4. Защита по току: RMS-измерение CT-трансформатора (**ADC w/ hardware monitor**), пороги stall/overload, время реакции <50 мс.
5. Анти-защемление: реверс при превышении тока/пропаже луча во время движения.
6. Замедление в концах хода (ramp-down по энкодеру, аналог distance1div3/distance2div3 — но без блокирующих while).
7. Мягкий пуск (pwm-ramp через MCPWM/LEDC либо ступенчатый релейный режим).
8. Счёт циклов, ТО-напоминания, журнал отказов.
9. Восстановление позиции после сбоя питания (NVS periodic checkpoint + endstops re-home).
10. Ручной режим (обход защит) с авторазблокировкой по таймауту.

### 3.2 Безопасность (то, чего STM32-версия не имеет)
11. **Secure Boot v2** (RSA-3072/ecdsa) + **Flash Encryption** (AES-XTS) — защита прошивки и конфигурации.
12. **WDT**: RTC watchdog (esp_task_wdt per-task) + независимый **WWDT**; автоматическая остановка мотора при зависании.
13. Отказоустойчивость: watchdog-пин для драйвера мотора (heartbeat), OFF при молчании CPU.
14. Двойная валидация концевиков (два чтения с интервалом + гистерезис).
15. Детект обрыва датчиков (pull-up/pull-down тест в idle).
16. Защита от повторных команд (command rate-limit, interlock OPEN/CLOSE одновременно).
17. Логи аварий в отдельный NVS/SPIFFS ring-buffer + core dump partition для отладки.
18. Tamper-detection: датчик вскрытия корпуса (GPIO wake) + запись в журнал.
19. Оповещение об отключении 220В (детект AC_PERIOD пропадания) + работа от Li-ion буфера (TP4056 + fuel gauge MAX17048 по I2C).

### 3.3 Связь и удалённое управление (главное преимущество S3)
20. **Wi-Fi STA** с авто-reconnect, приоритетом сетей, скан-выбором лучшей AP.
21. **SoftAP** режим для первичной настройки (provisioning) + mDNS `gate.local`.
22. **BLE 5 / NimBLE**: provisioning, управление со смартфона рядом с воротами, Long Range beacon.
23. **MQTT over TLS** (esp-mqtt): топики статуса/команд, LWT, Home Assistant auto-discovery.
24. **HTTPS REST API** (JWT/token auth) + встроенный **web-дашборд** (HTML/JS из SPIFFS/LittleFS, live-график тока через SSE/WebSocket).
25. **WebSocket** realtime-статус (позиция %, ток, события).
26. **SNTP** синхронизация времени + будильники/расписание (откр. к 7:00, закр. в 23:00, выходные-правила).
27. Telegram / email push-уведомления (SMTP client + bot API через HTTPS).
28. Интеграция умного дома: **Home Assistant (MQTT)**, **Tasmota-compatible**, опционально **Matter-over-Wi-Fi** (экспериментально на S3).
29. **RS-485 / Modbus RTU slave** для промышленных систем/охранной панели.
30. **TWAI (CAN 2.0)** шина для выносных постов управления, датчиков, нескольких ворот в сети.
31. **USB OTG / CDC** + USB-Serial-JTAG консоль (отладка без UART-адаптера).
32. Мультипользовательский доступ: PIN-коды, RFID RC522 (SPI), ключ iButton/Dallas (RMT/1-Wire), пароль-по-времени.
33. Гость-режим: временные токены/QR (генерация на экране OLED или отправка в мессенджер).

### 3.4 Идентификация и авто-открытие
34. **Bluetooth- Presence detection**: телефон владельца как метка (RSSI-геозона) → авто-открытие.
35. ESP-NOW mesh между устройствами (ворота + калитка + датчики) без роутера, дальность/низкая латентность.
36. Статус-LED RGB (WS2812) — цветовые коды состояний, эффекты при движении.
37. Голосовые уведомления через **I2S + DAC/усилитель** (MP3-decoder esp_audio) — «Ворота открываются».

### 3.5 Диагностика и обслуживание
38. **OTA update** A/B-partitions + checksum + авто-rollback, HTTPS с проверкой сертификата.
39. Удалённая консоль (esp-console / telnet/TLS shell) + команды диагностики (`dump enc`, `calib current`).
40. Самодиагностика при старте: тест реле, PCM-самотест ADC, ping датчиков; код ошибки на LED/beep.
41. Метрики производительности: heap, rssi, uptime, кол-во ребутов — в MQTT status topic.
42. Экспорт журнала событий (CSV из LittleFS по HTTP download или на SD-карту).
43. Калибровочный мастер-режим (wizard через web UI): число импульсов/оборот, токовые пороги, глубина замедления.
44. Профили пользователей/сценариев (утро/вечер/отпуск).

### 3.6 Энергосбережение (для автономного варианта)
45. **Deep-sleep** с пробуждением по кнопке/концевику (EXT0/EXT1 RTC GPIO) — дежурный режим <20 мкА.
46. Light-sleep во время ожидания завершения движения (мотор-контроллер держит heartbeat).
47. Управление питанием: MOSFET load-switch для Wi-Fi модуля/периферии по необходимости.
48. Battery telemetry (Li-ion 18650 + INA219 по I2C: V/I/SOC) + заряд через TP5000/TP4056.
49. Solar-friendly: MPPT-лайт логика (включение тяжёлых задач при полном заряде).

### 3.7 Расширенная логика ворот
50. Partial open («калитка»): открытие на N% для пешехода/входа.
51. Авто-закрытие с настраиваемым таймером + предупреждающий beep перед движением.
52. Синхронизация двух створок/секций (master-slave по ESP-NOW/CAN).
53. Интеграция с домофоном (сухой контакт → GPIO wake) и охранной сигнализацией (Dry contact in/out).
54. Интерлок с шлагбаумом/освещением (реле-выходы, GPIO 47/48…).
55. Расписание сезонных правил (RTC + NVS rules engine, cron-подобный парсер).
56. Гео-фенсинг через GPS-модуль (UART NMEA) — открытие только рядом с домом (доп. железо).
57. Камера-опция: ESP32-S3 поддерживает **DVP камеру (esp_cam)** — покадровый контроль въезда, JPEG по HTTP/MQTT (при наличии камеры OV2640; требует высвобождения пинов).
58. Детекция объекта по камере (TinyML/TF-Lite Micro on S3 — векторные инструкции) — экспериментально.
59. ML-классификатор состояния привода по профилю тока (простая модель на S3): раннее обнаружение износа ремня/смазки.

### 3.8 DevOps / надёжность системы
60. Версионирование в NVS + вывод версии в web/MQTT; changelog partition.
61. Загрузка конфигурации из JSON в LittleFS (hot-reload без перепрошивки).
62. Unit-тесты на хосте (Ceedling/Unity) для gate_logic/current_sense; HIL-тесты на целевом железе.
63. CI-скрипт сборки `idf.py build` + артефакты bin (Makefile — позже, как просили).
64. Статистика налёта часов работы реле/мотора → прогноз ресурса.

## 4. Маппинг старого кода → новые компоненты

| Текущий файл | Проблема при переносе | Решение на ESP32-S3 |
|---|---|---|
| `main.c` superloop + `brief.c` switch(timerClock) | блокирующий цикл | FreeRTOS-задачи + очереди событий; `esp_timer` для периодики |
| `motor.c` (реле, while-ожидания) | гонки, нет ШИМ | `motor_drv` на MCPWM/LEDC + state-machine, неблокирующие timeout |
| `init.c` (TIM3->CNT энкодер) | переполнение, прямой доступ к регистрам | **PCNT unit** (аппаратный quadrature, 32-bit) |
| `adc.c` (софтверный RMS) | шум, нагрузка CPU | ADC + **hardware monitor** (APB ADC filter), DMA-буфер |
| `button.c` (ошибочные условия) | баги debounce | конечный автомат кнопок (short/long/double) на GPIO-интрах + timer |
| `beep.c` паттерны | жёсткие массивы | LEDC-тон/NimBLE-RMT, паттерны в NVS |
| `rtc.c` (STM32 RTC) | потеря времени | **esp_sntp** + RTC (system_time) + будильники `esp_timer`/deep-sleep wake |
| `spi.c` (не использован) | мёртвый код | SPI → RFID RC522 / SD / дисплей ST7789 |
| `stm32f1xx_it.c` прерывания | HAL-specific | `gpio_isr_handler`, `pcnt_isr`, `mcpwm` fault ISR |
| `define.h` CONDITION-маска | неудобна | enum-state machine + event queue |
| `sys.c` Error_Handler | пусто | `esp_restart` + сохранение причины в NVS + core dump |

## 6. Ответы пользователя (зафиксировано)

1. **Силовой узел:** параллельная сборка «симистор + реле» (тринистор для фазового/плавного управления + реле для гальванической развязки/удержания).
2. **Энкодер:** три варианта аппаратной поддержки — оптический (quadrature), ДХ (эффект Холла), ДИ (индуктивный). Единый вход PCNT + конфигурируемый входной каскад.
3. **Каналы связи:** BLE + Wi-Fi.
4. **Камера:** распознавание автомобиля, номера, лица водителя, намерения выехать/заехать — с обучением на устройстве/облаке.
5. Питание и Secure Boot — см. п.7 ниже (решение принимается до первой прошивки!).

## 7. Уточнения по новым вводным

### 7.1 Силовой узел «симистор + реле» → implications для прошивки
- Симистор управляется фазово → нужен **синхронизационный вход** (проект уже имеет AC_PERIOD!): ловля перехода через ноль внешним прерыванием/GPIO-ISR; управление — угол открытия (phase-angle) либо burst-fire (целые полуволны). На ESP32-S3: гильза-таймер (esp_timer) + ISR по zero-cross, таблица углов; кривая «угол→момент» калибруется wizard'ом. Для асинхронного мотора ворот чаще предпочтителен burst-fire (меньше помех ЭМС, меньше нагрев симистора), phase-angle — только для мягкого пуска.
- Реле = выбор направления (реверс) / удержание / шунтирование симистора на полном ходу: **dead-time** между переключением реле и открытием симисторной ветви (реле коммутирует ТОЛЬКО обесточенную нагрузку!), счётчик циклов реле (NVS), защита от «реле залипло» (ток есть при запертом симисторе / нет движения по энкодеру).
- Обязателен **opto-triac + snubber**; прошивка предусматривает heartbeat-пин (драйвер сам симистора) и детект обрыва цепи нагрузки (ток есть, движения нет → клин; движение есть, тока нет → обрыв).
- Плавный пуск/останов реализуются естественнее, чем на STM32-реле: ramp по углу → мягкий старт, anti-pinch по току и энкодеру одновременно.

### 7.2 Энкодер: оптический / ДХ / ДИ
- Все три подаются в **PCNT** (у S3 8 независимых счётчиков, 2 фазы каждый): оптический — open-collector/5–24 В через делитель или оптопару; ДХ — обычно push-pull, возможен ШИМ-выход (тогда считать не импульсы, а скважность → отдельный режим); ДИ — синусоидальный сигнал → компаратор Шмитта с настраиваемым порогом. В конфиге NVS: тип датчика, инверсия, glitch filter, импульсов/оборот и импульсов/мм. Направление — по двум каналам PCNT (аппаратно), без софтверного дешифратора из прежнего проекта.
- Резервный канал: если основной энкодер нечитаем (обрыв ДИ) — переход на «time+current» оценку позиции.

### 7.3 Камера и ML — честная оценка нагрузки (S3 без NPU!)

Важно: ESP32-S3 **не имеет** акселератора (в отличие от ESP32-P4 с MIPI-ISP/NPU или AM62). Реальность для S3:
- esp-dl (официальная библиотека Espressif, int8, заточена под S3) — детекция лиц/глаз/рук, распознавание цифр/символов; ~кадры в секунду на VGA в PSRAM. Это рабочая база для face detect + простой OCR.
- Полноценный ANPR «госномер в потоке» и детект «намерения» на S3 — тяжело; правильная топология: **S3 = контроллер ворот + триггер**, тяжёлое зрение — на домашний сервер (OpenCV/YOLO/Frigate) или камеру со своим AI (Reolink/Hikvision/Dahua с ANPR). Схема: событие с камеры по MQTT/HTTP → решение о открытии на стороне S3 (или наоборот, сервер шлёт команду).
- On-device обучение классификаторов лиц/номеров нереалистично (нет памяти/вычислений); реализуемо: локальный whitelist (эмбеддинги лица из esp-dl + nearest-neighbor в PSRAM), дообучение «намерений» — сбор размеченных событий на сервере → переобучение → доставка .tflite/esp-dl-модели через OTA-подобный канал в model-раздел.
- OV2640 через DVP на S3 возможен, но жрёт GPIO и пин-конфликты с PCNT/MCPWM — при выборе камеры зарезервировать 12+ GPIO; альтернатива — ESP32-S3-EYE/QDtech как отдельный «глаз» в сети.
- Приватность: изображения не покидают локальную сеть; хранение локально (flash encryption), opt-in, кнопка wipe.

### 7.4 BLE + Wi-Fi (зафиксировано)
- BLE: provisioning, ближнеполевое управление (авторизация «по факту присутствия»), beacon-режим для presence-открытия. NimBLE (низкая RAM).
- Wi-Fi: STA+AP fallback, mDNS, web-дашборд, MQTT over TLS, SNTP, OTA. Роуминг/несколько SSID из NVS.

## 8. Что такое Secure Boot (и почему «необратимо!»)

Secure Boot v2 на ESP32-S3 — проверка **цифровой подписи (ECDSA-P256, не AES!)** каждой прошивки bootloader'ом на основе публичного ключа-корня (digest), записанного в eFuse чипа при первой активации. Цепочка доверия: ROM → bootloader (подпись проверяется корнем из eFuse) → app-раздел (подпись проверяет bootloader). Итог: без приватного ключа разработчика прошить устройство произвольным кодом невозможно — даже при физическом доступе и дампе flash.

**Почему «необратимо»:** запись eFuse — это выжигание предохранителей, отменить нельзя ничем. После включения SECURE_BOOT_ENABLE чип навсегда отказывается загружать неподписанные образы; после включения Flash Encryption flash навсегда шифруется ключом из eFuse (чтение дампа бесполезно). Потеря приватного ключа = невозможность выпустить ни одну новую легитимную прошивку для этого чипа. Поэтому: ключ генерируется вне устройства (`espsecure.py generate_signing_key`), хранится в HSM/зашированном бэкапе, включение тестируется на списываемом образце, для серии — единая политика ключей на производстве.

Рекомендация: опытный образец — НЕ включать (оставить возможность отладки/JTAG-дампа). Промышленная серия / уличные объекты с доступом третьих лиц — включать Secure Boot + Flash Encryption на этапе производства. Для ворот с Wi-Fi и OTA — как минимум подпись OTA-образов (`esp_ota` требует подписанный app при включённом Secure Boot) имеет смысл заложить сразу, сами eFuse включить позже.

### 9.1 Питание «сеть + батарея» → задачи прошивки
**Формулировка требования пользователя:** химия батареи не принципиальна; жёсткие требования — (а) работа в широком погодном диапазоне, (б) автономности хватает ровно на: уведомление в Telegram, журналирование и сохранение текущего состояния. Т.е. батарея = буфер «graceful shutdown + оповещение», а НЕ источник долгой работы. Это сильно упрощает и удешевляет проект.

**(а) Широкий погодный диапазон — что делаем в железе и прошивке**
- Диапазон цели: −40…+60 °C (класс «улица/гараж»). Выбор компонентов под него: промышленные ESP32-S3-WROOM-1-N16R8 (-40…+85 модуль), тантал/полимер вместо электролитов (электролиты на морозе теряют ёмкость), DC-DC с индуктивностями под -40 °C.
- Батарея — единственный температурно-чувствительный элемент:
  * LiFePO4: лучший компромисс (−20…+55 разряд, цикл стабильный); заряд только >0 °C (защита charge-IC по NTC).
  * Li-ion NMC: −20…+60 разряд, но деградация при заряде ниже 0 °C → обязательный thermal-interlock заряда.
  * Свинец/AGM: −20…+50, терпим к холоду, но деградирует при жаре и занимает место.
  * Для экстремального севера: нагревательный резистор + термоконтроль заряда (заряд разрешён только при T>5 °C) — дешёвое решение, включается редко.
- Датчик температуры (NTC 10k или DS18B20/I2C) рядом с батареей → в telemetry и в логи; пороги: charge-inhibit, thermal-warning.
- Конденсатор-держатель (supercap 0.1–0.3 Ф или электролит bank) — рассчитать под худший холод (ESR↑, ёмкость↓ на 30–50 % при −20 °C): запас ×2–3 от расчётных 100–200 мс.
- Влажность/конденсат: conformal coating платы; в прошивке — периодический self-check утечек (изоляция входов ADC), лог влажности если поставим SHT4x (опция).
- Герметичный уличный корпус, кабельные вводы, молниезащита/варистор на входе 220 В и на линии энкодера/концевиков (гальваническая развязка или TVS).

**(б) Автономность = «Telegram + журнал + сохранение состояния»**
Бюджет события «пропало питание» (референсный расчёт, уточняется после выбора батареи):
| Шаг | Действие | Время | Энергия (тип.) |
|---|---|---|---|
| 1 | Детект loss-of-mains (GPIO ext0-wake / компаратор) | <10 мс | — |
| 2 | Сохранить состояние ворот (позиция, флаги, счётчики) в NVS | 50–150 мс | ~0.1 Дж |
| 3 | Дожурналивать RAM-лог событий в NVS/flash (batched append) | 100–300 мс | ~0.2 Дж |
| 4 | Wi-Fi уже ассоциирован (kept-alive) → HTTPS POST в Telegram Bot API | 1–3 с | ~1–2 Дж |
| 5 | Подтверждение доставки → повтор при таймауте (max 2 ретрая) | +3 с | +1 Дж |
| 6 | Переход в deep-sleep (ext1 wake по возврату mains) | — | микроамперы |
Итого пик ≈ 2–5 Дж сверх того, что держит конденсатор-держатель + батарея в режиме ожидания. Отсюда спецификация:
- Конденсатор-держатель обязан гарантировать шаги 1–3 (≈0.5 Дж) даже при −20 °C — это и есть главный расчёт ёмкости; батарея покрывает шаги 4–5 (Wi-Fi-транзакция).
- Минимальная ёмкость батареи: 18650 2000 мАч (7.4 Wh) даёт огромный запас (десятки таких циклов); реально достаточно LiPo 500–1000 мАч или LiFePO4 1200 мАч. Химия — на вкус по климату корпуса.
- Политика: battery не для удержания контроллера «онлайн» часами — после отправки уведомления уходим в deep-sleep (<20–40 мкА), просыпаемся по ext1 на возврат mains и по RTC (heartbeat-разбудка раз в N часов для проверки живости батареи).
- Telegram-канал: отдельный component `notify_tg` — HTTPS + TLS, bot-token/chat-id в NVS; очередь уведомлений с дедупликацией (mains-fail не спамит при частых миганиях — debounce 30 с); fallback: то же сообщение через MQTT broker, если TG недоступен.
- Журналирование: кольцевой RAM-лог (быстрые записи без износа flash) + сброс в NVS по триггеру (событие/полчаса/loss-of-power); формат JSONL, экспорт по HTTP из web UI.
- Если Wi-Fi не успел подняться (роутер тоже обесточен) — фиксируем «pending notification» и отправляем при первом подключении после восстановления mains; в журнале помечаем «notified late».
- Тест приёмки: cold-soak −20 °C → имитация пропадания питания → проверка, что (1) состояние сохранено, (2) лог дописан, (3) TG-сообщение доставлено ≤10 с, (4) устройство уснуло и проснулось по возврату.

**(в) Прочие задачи power_mgmt (без изменений)**
- Мониторинг сети: детект пропадания 220 В → событие, удержание/безопасная остановка ворот по политике, оповещение о возврате.
- Заряд: charge-IC (TP4056/LiPo, BQ25895 с I2C-телеметрией, или простой linear + ADC делитель) + thermal interlock из (а).
- Пороги батареи: warning/critical только для «не спать слишком глубоко» и алерта «батарея мертва» (тоже через TG при живом mains).
- Light-sleep vs deep-sleep: на mains — лёгкий сон CPU0; от батареи после нотификации — deep-sleep.

### 9.2 Secure Boot выключен — что всё равно делаем сейчас
- Разделы подписанных OTA-образов конфигурируем заранее (`esp_ota` + signed artifacts в CI), чтобы включение eFuse позже не требовало смены процесса сборки.
- Пароли/токены/MQTT-клиентские секреты НЕ храним в открытом виде «в коде»; только NVS (после включения Flash Encryption станут защищены автоматически).
- Debug-логирование и консоль закрываем флагом сборки release (на серии с включённым SB/JTAG аппаратно disabled).
- Риск без SB: физический доступ → дамп flash → извлечение Wi-Fi credentials и ключей API. Митигация до eFuse: локальные пароли, whitelist MAC, TLS-only наружу.

## 10. Камера на плате: минимальный И производительный функционал распознавания

### 10.1 Железо и бюджет ресурсов
- OV2640 (2 Мп, DVP 8-bit) — оптимум S3; OV5640 если нужна автофокус/лучше ночь. ~12–14 GPIO под DVP → резервируем в пин-карте сразу (конфликт с PCNT/MCPWM решается на этапе разводки платы).
- Питательный бюджет: Wi-Fi + camera active ≈ 300–500 мА — на батарее это часы, поэтому камера работает по триггеру, а не постоянно (см. п.10.3).
- Кадр: QVGA/VGA в PSRAM; esp-dl int8-модели; 240×240 типовой вход сети.

### 10.2 Реалистичный on-device стек (esp-dl / ESP-WHO + собственные int8-модели)
| Задача | Модель/метод | Скорость на S3 (240 МГц, int8) | Статус |
|---|---|---|---|
| Детекция объекта «автомобиль» | MobileNetV1/V2 SSD int8 или YOLO-fast прунед | ~1–3 кадра/с (QVGA) | ✅ реализуемо |
| Детекция лица | esp-dl Face-Detection (HOG/CNN) | реального времени достаточно | ✅ штатно ESP-WHO |
| Распознавание номера (ANPR) | детект ROI → сегментация символов → CNN-классификатор цифр/букв | пайплайн ~1–2 с на кадр | ⚠️ базово: хорошо при свете/фронте; ночью/под углом — плохо |
| Whitelist лиц (не full face-ID) | 128-D эмбеддинги (ArcFace-подобная, квантованная) + nearest-neighbor в PSRAM | <100 мс на сравнение | ✅ до сотен лиц |
| Намерение «выезжает/заезжает» | не DL-сеть, а трекинг: bbox-фильтр Калмана + правило вектора скорости/пересечения зоны (polygon intrusion) | почти 0 mcycle | ✅ надёжнее чистого ML |
| Класс «номер распознан полностью» | эвристики confidence + повторы кадров | — | ✅ |

Что честно НЕ тянет S3: полноценный свёрточный ANPR в ночном потоке, face-ID в базе тысяч, video-LLM «понимание сцены». Для апгрейда — внешний сервер/IP-камера по MQTT (архитектура п.7.3 сохраняет оба пути).

### 10.3 Производительность: событийная работа камеры (key idea)
1. Дежурный режим: камера выключена/низкий FPS (5 fps QVGA) + дешёвый детектор движения (разность кадров в psram, либо PIR/Pcnt-триггер от шлагбаума).
2. Триггер (движение в зоне / presence BLE / кнопка «видео») → подъём до 15–25 fps VGA, запуск пайплайна auto→plate→face→intent.
3. Решение за ≤1–2 с: совпадение whitelist-номера/лица + намерение «въезд» → команда gate_logic open; иначе — лог + snapshot (опционально).
4. Idle-потребление с выключенной камерой падает в разы; дежурный low-FPS режим — компромисс, отключаемый политикой на батарее.

### 10.4 Обучение и калибровка («с обучением» — как реализуем)
- Локально: регистрация лиц/номеров владельцем (web UI → снятие эмбеддингов → NVS/model-раздел). Whitelist = «обучение на устройстве» в практичном смысле.
- Серверно (opt-in): сбор размеченных кейсов (ложные срабатывания) → переобучение инт8-модели на PC/GPU → доставка модели в dedicated partition + hot-swap (не bootloader-OTA, просто файл модели). Версионирование моделей, rollback.
- Калибровка зон: web-дашборд рисует polygon «дорога/вход/стоп-линия» поверх live-кадра → сохраняется в NVS.

### 10.5 Приватность и безопасность данных камеры
- Snapshot'ы — только локально (SD/flash), шифрование policy-based, авторетention (N дней), кнопка wipe.
- Никакой передачи видео в облако без явного opt-in; TLS-only; face/plate данные помечаются как PII в конфиге.

## 12. Спецификация распознавания (финальная, по ответу пользователя)

### 12.1 Два целевых сценария (state-machine уровня «визор»)

**СЦЕНАРИЙ А — «Подъезд разрешённого автомобиля» → ОТКРЫТЬ:**
Все условия (или настраиваемое подмножество — голосование с весами):
| # | Признак | Реализация on-device | Стоимость |
|---|---|---|---|
| A1 | Автомобиль подъезжает к воротам | det «car» (esp-dl SSD int8) + трекинг bbox (Калман) + вектор скорости направлен к воротам + пересечение polygon-зоны «подход» | 1–3 к/с, OK |
| A2 | Марка/цвет | цвет — HSV-гистограмма ROI (дёшево, надёжно); марка — мелкая int8-классификация cropped-ROI (MobileNetV3-small ~30–100 классов топ-марок) | +50–150 мс на кадр-кандидат |
| A3 | Госномер совпадает с базой | ANPR-пайплайн (детект ROI → OCR символов) + fuzzy-сверка с whitelist (до ~200 номеров в PSRAM) | 1–2 с на событие, ⚠️ качество зависит от света |
| A4 | Особые приметы (стилинг, повреждения) | НЕ отдельная DL-сеть: эмбеддинг заднего/переднего вида авто (квантованный feature-vector) → nearest-neighbor к «отпечатку» конкретного экземпляра из базы. Повреждения/тюнинг ловятся самим фактом совпадения эмбеддинга «этого экземпляра», а не классификацией «бампер помят». Регистрация примечаний — через web UI («обучение» экземпляра по 3–5 кадрам) | <100 мс на сравнение |
| A5 | За рулём человек из базы | esp-dl Face-Detect в зоне окна (ROI по позиции A1) + 128-D эмбеддинг + NN-сверка whitelist лиц | реалтайм, OK |
| A6 | Включены ходовые огни | дешёвая эвристика: яркость/контраст двух симметричных ROI фар (threshold + blob-анализ), калибруется при регистрации экземпляра; ночью — инвертированная проверка (огни ОБЯЗАНЫ быть) | ~0 mcycle |
→ Решение ≤2 с от входа в зону. Порог открытия — настраиваемый взвешенный скор (например: номер 0.4, лицо 0.25, экземпляр-эмбеддинг 0.2, presence+движение 0.15) + политика «неизвестное авто → только лог/snapshot, не открывать».

**СЦЕНАРИЙ Б — «Автомобиль преодолел ворота» → ЗАКРЫТЬ:**
| # | Признак | Реализация |
|---|---|---|
| B1 | Пройдена стоп-линия / polygon «внутри» | трекинг bbox пересекает линию наружу→внутрь (уже считаем в A1) |
| B2 | Видны задние огни | blob-детект двух красных ROI (HSV red mask + геометрия пары) |
| B3 | Задний номер читается и совпал ранее | подтверждение идентичности объекта трекинг-ID (не повторный ANPR: ID из сценария А несём через всю траекторию; ANPR повтариваем опционально для самопроверки) |
→ Команда close c гистерезисом: ворота НЕ закрываем, пока bbox машины внутри зоны или ток мотора/энкодер не подтвердили ход; закрытие — по таймауту «объект покинул кадр + огни подтверждены» (fallback: чистый таймер, как сейчас, но с camera-override).

Важно: сценарий Б превращает камеру в **датчик присутствия автомобиля в проёме** — это одновременно функция безопасности (анти-защемление из п.3 Этап 3 теперь имеет второй независимый канал подтверждения, кроме тока).

### 12.2 OV5640 без IR — честные следствия
- OV5640 (5 Мп) vs OV2640: выше разрешение → лучше читаемость номеров (главный выигрыш именно для ANPR); сенсор 1/4″, чувствительность сопоставима — **без подсветки ночью/в сумерках ANPR деградирует резко** (это физика, не софт).
- ИК-решение ДОПУСТИМОЕ и рекомендуемое: OV5640 механически cut-фильтруемый — многие модули снимают IR-cut вручную + внешний IR-LED 850 нм (или 940 нм — невидим, но темнее). Для сценариев А/Б это работает ДАЖЕ ЛУЧШЕ дневного варианта: ходовые/задние огни на 850–940 нм светятся ярко (светодиодные фары дают сильный ИК-контраст), номера с retro-reflective-плёнкой возвращают засветку подсветки → читаемость растёт. Т.е. «если решается дополнительным ИК СИД» — **да, решается**, и это самый дешёвый путь к ночному режиму (IR LED 3–5 Вт + питание от mains-буфера, включаем синхронно с активацией камеры; на батарею после loss-of-mains камера и IR не включаются вообще).
- Без IR ночью остаётся: детект «автомобиль» по силуэту/огням (работает — огни видимы), трекинг и сценарий Б по огням — работают; полноценный ANPR — нет → политика: ночью порог сценария А повышаем (требуем номер+лицо днём, ночью — номер ИЛИ эмбеддинг экземпляра + огни), либо «ночной режим = только пассивный лог».
- Профиль камеры в NVS: resolution/fps/HDR/wb/expo по времени суток (день/сумерки/ночь) + экспозиция с приоритетом короткого выдерживания для стоп-кадров ANPR.

### 12.3 Что УБИРАЕМ из стека (по ответу)
- ❌ Детект пеших людей / vandal-детект — убираем из v1 (освободившиеся CPU-циклы → в пользу частоты ANPR-повторов).
- ❌ «Намерение пешего», face-ID общей базы — нет; лица только в связке «водитель из whitelist».
- ✅ Остаётся ядро: car-detector + tracker/polygon + color-histogram + mark-classifier (опц.) + ANPR + face-whitelist(NN) + instance-embedding(приметы) + light-heuristics.

### 12.4 Модельный ряд и «обучение» (уточнение под новые признаки)
- База экземпляров авто (для A3/A4): регистрация в web UI — владелец загоняет своё авто в зону → система сама снимает 5–10 кадров → формирует (а) OCR-номер, (б) HSV-цвет, (в) эмбеддинг внешнего вида, (г) профиль огней; всё ложится в NVS/model-раздел как «vehicle profile». Это и есть «обучение particular'а» без сервера.
- Классификатор марки — предобученная int8-модель (доставляется как файл модели, hot-swap, версионирование — п.10.4); дообучение под конкретный региональный парк — серверный цикл opt-in.
- Лица водителей — та же схема, что в п.10.4 (эмбеддинги, локальная регистрация).

### 12.5 Обновлённая карта зависимостей компонентов
camera_pipeline → vision_core (det/track/anpr/face/embed) → gate_logic (события VEHICLE_APPROACH_OK / VEHICLE_INSIDE / VEHICLE_LEFT) → motor_drv; параллельно current_sense/encoder как независимое подтверждение (cross-check: camera-«машина в проёме» И энкодер «полностью открыто» → ждать; противоречие → safe-state + алерт).
